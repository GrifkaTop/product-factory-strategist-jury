# Порядок работы с кейсом

Норматив схем и операций — [контракт реализации](../docs/IMPLEMENTATION_CONTRACT.md). Правила кейса не блокируют разрешённую разработку репозитория.

## Начало и следующий шаг

1. Установи `case_id`, полномочия пользователя, исходный запрос и границы. Сохрани запрос дословно в [brief](../templates/brief.md). Не переносись в чужой кейс.
2. Проверь доступность локальных инструментов. Используй фактический CLI и его справку из README/реализации. Планируемые в PRODUCT_PLAN команды не считаются существующими; этот пакет не вводит новых команд. Если нужной операции нет, сообщи пробел, не имитируй сохранение.
3. Пройди `intake → research_plan → evidence → options → strategies → validation → complete`. Загружай только нужную методику и источники. Сначала исследование и выбор, затем утверждённые стратегии.
4. Уточняй только блокирующую неопределённость; обычно достаточно 1–3 вопросов. Остальное помечай допущением и продолжай обратимый шаг.
5. После законченного шага сохрани реестры, артефакты и `next_action`, проверь результат сохранения. Покажи краткий результат и что осталось неизвестным.

## Локальный CLI

Синтаксис ниже подтверждён справкой текущей реализации 17.11.2026. Выполняй команды из корня репозитория; `example-case`, `source.md` и `change.json` — подставляемые ID/пути, готовых файлов они не обещают. Порядок определяется стадией: apply требует подготовленного изменения и актуальной revision, а pause/resume — намерения пользователя.

```text
python -m tools.strategist doctor
python -m tools.strategist init --case example-case
python -m tools.strategist ingest --case example-case --file source.md
python -m tools.strategist status --case example-case
python -m tools.strategist apply --case example-case --input change.json
python -m tools.strategist validate --case example-case
python -m tools.strategist validate --case example-case --ready
python -m tools.strategist pause --case example-case
python -m tools.strategist resume --case example-case
```

`status` читает состояние, `apply` записывает изменение, `resume` явно снимает паузу. `doctor` проверяет локальную среду, но не доказывает доступность модели/поиска. Проверка синтаксиса не заменяет полный прогон кейса. CLI не рассуждает и не утверждает выбор вместо человека.

На стадии `validation` перед записью `complete` запусти `validate --ready`. Устрани найденные блокеры в актуальной ревизии: ошибка `completion.output_missing` указывает путь к отсутствующему или пустому результату. Проверка читает сохранённый снимок, состояние кейса остаётся доступным для следующих шагов. `complete` записывается отдельным подтверждённым переходом.

## Согласование

Перед утверждением направления подготовь [decision-memo](../templates/decision-memo.md): вопрос, минимум три содержательно разных варианта, рекомендация, основания, возражения, цена ошибки, неизвестность и следующий шаг. Обычно сравни четыре варианта; status quo и закрытие/отказ рассматривай обязательно. Для существенной смены цели, бюджета или публичного обещания получи новый ответ человека. Подготовка и критика черновика в разрешённой задаче нового разрешения не требуют.

Сохрани `status=awaiting_human`, пока ответа нет. «Сделай исследование» не равно выбору продукта. При неоднозначном ответе уточни выбор; не назначай вариант по умолчанию. В учебном демо капитан выбирает от своего имени, без имитации согласования компании.

Различай конкурсный продукт-агент и вымышленный продукт внутри учебного стенда. Не делай согласование вымышленного направления условием продолжения разработки агента. Можно подготовить и проверять явно условные черновики без утверждения направления; оставляй кейс до human gate и продолжай независимые технические задачи. Если пользователь уточняет смысл вопроса, это не является выбором и не записывается как approval.

Запись выбора — только `kind=human_decision` с `id`, существующим `selected_option_id`, точным непустым `user_response`, `options_hash`, `rationale`. Хеш вычисляется по текущему списку `registries.options`: SHA256 от UTF-8 `json.dumps(options, ensure_ascii=False, sort_keys=True, separators=(',', ':'))`. Не копируй хеш из прежней версии. Это запись наблюдаемого ответа, а не подтверждение личности. `patch` не может создать approved decision.

## Сохранение и продолжение

- Состояние: `schema_version=1`, `case_id`, `revision`, `phase`, `status`, `goal`, `next_action`, `registries`, `artifacts`, `operations`. Реестры: sources, claims, hypotheses, gaps, options, decisions, promises, experiments. Не добавляй вымышленные обязательные поля схемы.
- Изменение: `schema_version=1`, уникальный `operation_id`, актуальный `expected_revision`, `kind`, `payload`. `patch` меняет только разрешённые контрактом поля; реестры обновляются по `id`. Повтор того же сохранения использует тот же operation ID и содержимое; иное содержимое — новая операция.
- Markdown сохраняй как текст UTF-8 в `artifacts` по безопасным относительным путям `outputs/<имя>.md`. Рабочие outputs и JSON — проекции. Не исправляй их вручную как отдельную истину и не редактируй immutable checkpoint.
- Только проверенный checkpoint с полным state и manifest определяет согласованную версию. Изменения одного кейса выполняет один писатель. После конфликта revision перечитай состояние, затем осмысленно пересобери изменение.
- По просьбе «сохрани и остановись» заверши текущее безопасное сохранение, укажи следующий шаг и поставь `paused`. В paused допустимы чтение и явное возобновление; apply/ingest не выполняй.
- Новый чат читает [resume](../prompts/resume.md), проверенное состояние, brief, актуальное решение и пробелы. Не нуждается во всей истории чата. Неподтверждённое сохранение не объявляй успешным. `recovery_warning` явно сообщи; восстановленный checkpoint не дополняй догадками о потерянной работе.
- Изменившиеся sources/claims/options делают прежний выбор `needs_review`. Проследи зависимости до расчётов, обещаний и экспериментов вручную в P0; покажи причины и передай существенный пересмотр человеку. Не обещай автоматический обход зависимостей.

`complete` означает готовность текущей версии результатов, а не рыночный успех. Для strategies/complete нужен актуальный approved decision. Допустимые status: active, paused, awaiting_human, needs_review, complete. Время фиксируй ISO8601 с часовым поясом.

## Экономия и отчётность

Модель рассуждает в текущей среде; Python выполняет механические операции без вызовов модели. Не обходи квоту внешним API. Записывай доступные время, режим модели и расход ресурса; недоступный расход помечай «неизвестно». Роли одной модели и короткий review субагента не являются независимыми подтверждениями фактов. Прочие чаты и массовое дублирование разработки не создавай.

Если человек задал наблюдаемый лимит для кейса, внеси его как `budget_limits` в файл замера и проверяй через `measure` перед затратными шагами. На 80% предупреди и уточни объём оставшейся работы. При достижении лимита сохрани завершённый шаг, останови затратную работу и запроси решение о следующем шаге. Если показателя нет, сообщи об этом и согласуй наблюдаемую замену, если без неё нельзя соблюдать лимит. Лимиты кейса задаёт человек. CLI сравнивает переданные значения и не считывает остаток недельной квоты.
