# Начать кейс

Начни новый кейс по дословному запросу пользователя и перечисленным им разрешённым материалам. Если пользователь не указал `case_id`, сам выбери короткий свободный ID. Это постановка задачи, не утверждение продуктового направления.

Прочитай [AGENTS](../AGENTS.md) и правила по его ссылкам. Проверь фактические локальные инструменты; не обещай команды из плана, которых ещё нет. Не перезаписывай существующий кейс: при совпадении ID уточни намерение или продолжи его по явному запросу.

Сохрани запрос дословно, сформулируй решение, получателя, аудиторию/задачу, горизонт, ограничения и достаточность исследования по [framing](../methods/framing.md). Задай только блокирующие вопросы; неблокирующие неизвестные сохрани как assumptions/gaps. Если именно этот кейс должен выполняться по конкурсному демобрифу, уточни его наличие отдельно от общего задания. Для обычной новой задачи достаточно разрешённых входов пользователя; дополнительный конкурсный бриф не запрашивай. Учебные данные не называй бизнес-фактами.

Подготовь [brief](../templates/brief.md) и [research-plan](../templates/research-plan.md) с вопросами, ответы на которые меняют выбор, минимальным доказательством и условием остановки. Сохрани завершённый шаг через инструменты состояния, проверь результат и укажи next_action. Продолжай разрешённые обратимые шаги. До исследования и реального выбора человека окончательную стратегию не утверждай.

Перед передачей вариантов человеку проверь сохранённую стадию и доказательства. В CLI проходи через соседние стадии по порядку. Сохрани опорные claims со связями на источники ещё на стадии evidence, до фиксации решения. Перед выбором проверь реестр обещаний, когда для рекомендуемой развилки уже предложен клиентский текст: укажи подтверждённую возможность, черновой план или блокировку. После фиксации решения добавление или изменение оснований может потребовать пересмотра.

После первого подтверждённого сохранения сообщи ID, стадию и ревизию, какой результат сохранён и какой шаг следующий. Дай готовую фразу для нового чата в этой же папке: «Продолжи кейс ⟨фактический case_id⟩». Если сохранить не удалось, сообщи причину и фактический статус.

Перед первым сохранением проверь `doctor.checkpoint_rename` в выбранном корне. При отказе сообщи `storage_hint`. При ошибке записи checkpoint сначала проверь текущую подтверждённую ревизию. Если рабочая папка запрещает атомарное переименование, продолжай тот же кейс с последней подтверждённой версии в разрешённой локальной копии. Укажи её путь и ID: оба понадобятся при возобновлении.
